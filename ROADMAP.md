# Arete — план по фазам (ROADMAP)

> На русском: язык автора. Английский перевод появится к релизу 0.1.

**Статус:** фазы 0–3 выполнены 21.10.2026 (SPEC v1, GRAMMAR, сквозной срез `arete run hello.rt`). Следующая — фаза 4.

Источник: Arete_plan.pdf («итог переписки», 19.10.2026, Karim Huseyn).
Состояние на 19.10.2026: репозитория arete нет; fryrrosx/fryrrosx — это README профиля.
Язык реализации: PDF фактически выбрал C11 + Makefile (CLAUDE.md, «Первое задание», структура репо). Rust — только если ты осознанно меняешь это решение.

Обозначения:
- «Решаем вместе» — вопрос синтаксиса или семантики, который PDF не закрыл. Решение принимаешь ты, я даю варианты и последствия.
- «Готово» — проверяемый критерий: позитивный тест (.rt + .expected) и негативный (.rt, который обязан упасть с конкретным текстом ошибки).
- «Читать» — что прочитать до шага «план» этой фазы. CI = Crafting Interpreters (Nystrom). Часть II там на Java, мы пишем на C, поэтому главы про массивы/строки/хеш-таблицы из части III читаем рано.
- «(не из PDF)» — моё предложение, не решение из переписки.

Где именно мы «разбираем все синтаксисы»: четыре сессии решений (фазы 1, 9, 19, 26) + шаг 1 ритуала в каждой фазе. Синтаксис конструкции закрывается окончательно в её фазе, а не заранее.

## Ритуал одной фазы (одинаков для всех)

1. Разбираем синтаксис: 2–5 примеров .rt «как будто язык уже есть». Варианты, последствия, твоё решение.
2. Ты сам пишешь тесты фазы до кода: один позитивный, один негативный (ошибка с файл:строка:колонка и подсказкой).
3. Фиксируем: строка в таблице SPEC.md (статус «закрыто в фазе N»), правило в GRAMMAR.md, проверка новых правил на пересечение первых токенов и левую рекурсию.
4. Я показываю план реализации (файлы, функции, структуры данных), ты одобряешь.
5. Код + тесты. `make test` и `make examples` зелёные. Комментарии в коде по-английски.
6. Сверка GRAMMAR.md с парсером: каждое правило EBNF = функция парсера, расхождения чиним сразу.
7. Разбор кода по-русски: как устроено, почему так. Твои вопросы.
8. Твоё упражнение по образцу «Challenges» из CI: например, в фазе 4 я делаю `+ - * /`, ты сам добавляешь `%` и тест.
9. `git tag phase-NN-name`, строка в CHANGELOG. Фаза закрыта только после пункта 8.

Правило остановки: если реализация показала, что решение из SPEC.md плохое, фаза останавливается, обсуждаем, правим SPEC с пометкой «ревизия в фазе N». Молча решения не меняются.

### Фаза 1. SPEC.md v1 — решения этапа B + 20 примеров-целей
Первая сессия синтаксиса. Переносим таблицу решений из PDF (раздел 2) как есть, у каждой строки статус: «из PDF / черновик / закрыто в фазе N».
Решаем вместе (нужно уже для этапа B):
- Заголовок `arete X.Y`: формат, можно ли комментарии/пустые строки до него. Что значит `arete 1.0` для тулчейна 1.1: запускать или требовать ровно 1.0.
- Номер версии и совместимость — решаем здесь один раз, до первого теста фазы 3: примеры PDF начинаются с `arete 1.0`, а план выпуска — «0.1, потом 1.0». Какой заголовок у файлов до 1.0; правило совместимости файла и тулчейна (при 0.x ломающие изменения живут в minor, поэтому «совпадает major» там не работает); что делать, если подключаемый модуль объявляет другую версию.
- Комментарии: `#`; многострочные нужны ли. Служебная строка примеров `# runs-after: phase N` стоит второй строкой, после заголовка версии.
- Точка входа: скрипт сверху вниз (Python) или `fn main()`.
- Отступы: только пробелы или табы тоже; ширина.
- Базовые типы: `int`, `float`, `string`, `bool`, `null`; размер `int` (64 бит), переполнение.
- Операторы: `+ - * / %`, поведение `/` на int (целочисленное деление), `**`; битовые операторы нужны ли (от этого зависит, встречается ли `>>` вне типов); `and/or/not` или `&&/||/!`; `==`/`!=`.
- `if` и `when` как выражения (одно решение на обе конструкции, как в Kotlin) или только операторы.
- `print` — встроенная функция или оператор.
- Строковые литералы: кавычки, escape-последовательности. Интерполяция `"{x}"` — литеральные скобки, вложенные выражения (реализация в фазе 11, но лексер проектируем в фазе 4).
- Зарезервировать слова и знаки на вырост: `class interface data enum sealed open pub use allow import fn let var if elif else while for in when is as try catch throw throws rethrows finally defer macro spawn select unsafe weak super self this`, аннотации `@name` (из `@gpu`), знаки `? ?. ?? -> => .. ..<` и `!` после идентификатора (возможный маркер макроса, фаза 26).
- 20 примеров-целей: по одному на конструкцию, в шапке `# runs-after: phase N`. Лежат в `examples/pending/`, при прохождении переезжают в `tests/`.
- Готово: SPEC.md с таблицей (у каждого решения есть пример) и 20 примерами с ожидаемым выводом в комментарии.

### Фаза 3. Сквозной срез: hello.rt работает (= «Первое задание» из PDF)
- CLI: `arete run file.rt`; `arete 1.0` → однострочный REPL без истории; `arete` → `error: version required` с `usage` и `installed: 1.0`; `arete 2.0` → `not installed`.
- Решаем вместе: раскладка на будущее — один бинарь с таблицей версий сейчас, позже лаунчер ищет `~/.arete/versions/<ver>/` и запускает нужный. Заголовок файла сохраняется в контексте компилятора как «edition».
- Проверка первой строки; без неё — `missing version header` с номером строки и подсказкой.
- Лексер только для: заголовка, чисел (нужны уже для `1.0` в заголовке), строк, идентификаторов, скобок, NEWLINE, комментариев `#` (пропуск). Позиция (строка, колонка) у каждого токена с первого дня. Арифметика — в фазе 4.
- Парсер + интерпретатор только для `print("строка")`.
- Решение по памяти с первого дня (PDF: подсчёт ссылок): `Value` = tagged union (тег + 8 байт), объекты в куче с полем `refcount`, `retain/release`. Циклы — в фазе 29. Это снимает переписывание в фазах 27–29.
- Эти `Value`/`retain`/`release` сразу оформляем как первую версию публичного заголовка `arete_rt.h`: всё, что потом станет стандартной библиотекой (строки в 11, коллекции в 12, модули в 21), пишется только через него, иначе под VM и LLVM её придётся переписывать.
- Читать: CI гл. 4 (сканер), гл. 14 (динамический массив на C), гл. 19 (строки на C).
- `tests/promote.sh`: переносит прошедший пример из `examples/pending/` в `examples/` и создаёт `.expected` (или `.expected_error`) из комментария в конце файла.
- Готово: `tests/hello.rt` → `Hello, World!`; `tests/no_version.rt` → ошибка с подсказкой; `arete` без версии → ошибка; `make build && make test`; `01_hello.rt` продвинут в `examples/`.

### Фаза 4. Числа и выражения
- Парсер Пратта: `int` и `float`, `+ - * /`, унарный минус, скобки, приоритет, ассоциативность (`%` — твоё упражнение). Ошибки времени выполнения с позицией (деление на ноль).
- Флаги `--dump-tokens` и `--dump-ast`: главный инструмент, чтобы видеть, как устроен язык.
- Проектные решения лексера (записать сейчас, реализовать когда понадобится): NEWLINE/INDENT не выдаются внутри `( [ {`; число не съедает `.` если дальше `.` (`1..10`); если битовые сдвиги решены в фазе 1, `>>` расщепляется парсером в позиции типа (`Map<string, List<int>>`); строка лексится на части `STRING_START / PART / INTERP_START / INTERP_END / STRING_END`; комментарии сохраняются как trivia у токена (нужно форматтеру); API потоковый `lex_feed_line()` + состояние «ввод не завершён» (нужно REPL).
- Читать: CI гл. 5–7; статья Nystrom «Pratt Parsers: Expression Parsing Made Easy»; Ball «Writing an Interpreter in Go», гл. 2 (Pratt-парсер) как второй взгляд.
- Готово: дамп AST `(+ 1 (* 2 3))` и `(* (+ 1 2) 3)` в `.expected`; `1 + 2 * 3` → `7`; `1 +` → `error: expected an expression, found end of line` с колонкой (форма сообщений парсера из фазы 3).

### Фаза 5. let / var и грамматика типов
- Объявление, присваивание, присваивание в `let` — ошибка. Временно ловим через таблицу имён (флаг `is_mutable`), окончательно — в резолвере (фаза 7d). Это временное решение записываем честно.
- Пока только глобальная область: блоков в языке ещё нет. Тесты на вложенные области — в фазе 6.
- Грамматика типов (парсим в узел `TypeExpr`, проверяем позже): `Type := Union; Union := Postfix ('|' Postfix)*; Postfix := Primary '?'*; Primary := Name ('<' Type {',' Type} '>')? | 'fn' '(' [Types] ')' ['->' Type] ['throws' [Name]] | '(' Type ')'`. Место под `throws` в типе функции нужно фазам 9 и 14.
- Решаем вместе: затенение (повторный `let x`) в файле — ошибка; в REPL — разрешено.
- Читать: CI гл. 8, гл. 20 (хеш-таблицы на C — окружение переменных).
- Готово: `let/var` тесты; `let x = 1; x = 2` → `error: cannot assign to immutable 'x'` с подсказкой «use var»; аннотации `let xs: List<int?> | string` парсятся в дамп AST.

### Фаза 7. Циклы, функции, резолвер
- 7a. `while`, `for x in`, диапазоны, `break/continue`. Внутренний протокол итерации (`iter/next` или индекс+длина), `Range` через него — коллекции в фазе 12 пойдут тем же путём. Решаем вместе: `0..10`, `0..<10`, `range(10)`. Негативный тест: `break` вне цикла.
- 7b. `fn name(a: int, b: int = 0) -> int:`, `return`, рекурсия, значения по умолчанию, аргументы по имени. Решаем вместе: видимость `fn` объявленных ниже (двухпроходный сбор объявлений как в Go/Kotlin) или строго сверху вниз.
- 7c. Функции как значения и замыкания (в PDF не названы, но на них опираются `when`-выражения, `rethrows`, VM и LLVM — принимаем как решение). Решаем вместе только синтаксис: лямбды в языке с отступами — однострочная `fn(x) => x * 2` и блочная только последним аргументом через «двоеточие + отступ»; захват по ссылке или по значению. Фигурные скобки `{ x -> }` конфликтуют с литералом Map и интерполяцией; `->` конфликтует с ветками `when`. Блочная лямбда внутри скобок конфликтует с правилом SPEC «внутри `( [ {` отступы не выдаются»: варианты — без блочных лямбд (вложенная именованная `fn`), хвостовой блок после закрывающей скобки, исключение в лексере. Записать связь с фазой 29: замыкания создают циклы ссылок.
- 7d. Резолвер (CI гл. 11): статическая привязка имён, глубина окружения, `let` проверяется статически, замыкания работают правильно.
- Читать: CI гл. 10–11.
- Готово: `fib(20)`; негативные тесты на лишний аргумент и на классическую ошибку замыкания из CI гл. 11.

## ЭТАП C — Язык растёт (PDF шаг 7, по одной конструкции)

### Фаза 9. SPEC.md v2 — синтаксис этапа C (вторая сессия)
Решаем вместе, с примерами на каждый пункт:
- Строки: методы, срезы.
- Коллекции: литералы `[1, 2]`, `{"a": 1}`; что такое пустой `{}` (Map или Set — ловушка Python); имена `List/Map/Set`; изменяемость: `let xs = [1]; xs.add(2)` разрешено? Вариант Kotlin: `List<T>` неизменяем, `MutableList<T>` изменяем (это же даёт правило «в канал только неизменяемое» в фазе 30).
- `when`: с субъектом и без; ветки литерал/диапазон/`is Type`/`null`/`else`/несколько значений; блочная ветка `-> :` + отступ (выражение или оператор — решено в фазе 1).
- Ошибки: `throws` с типом (`throws IOError`) или без (как Swift); что можно бросать (только `Error` или любое значение); `finally`/`defer`; `rethrows` для функций, принимающих бросающие замыкания.
- Классы: `self` или `this`; синтаксис конструктора; `class Circle: Shape` для интерфейса; имена методов data class (`toString`/`copy` — свои, не копия Kotlin); `enum` и/или `sealed class` (не из PDF; без них `when` теряет половину смысла).
- Null: `T?` = `T | null`; `?.`, `??`; где работает умное приведение.
- Generics: `List<T>`, `class Box<T>`, `fn first<T>(...)`, `T: Comparable`; явные аргументы при вызове `res.json<User>()` — неоднозначность с `<`: turbofish `json::<User>()` или lookahead «после `<` идёт тип и затем `>(`» с запретом `a < b > (c)`; модель: пример `json<User>()` требует либо дескриптора типа во время выполнения (reified; в LLVM мономорфизация), либо `inline`-функций с reified-параметром поверх стирания, как в Kotlin.
- Модули: `use` — свой код и пакеты Arete, `import <lang>` — чужой код; грамматика `use StringLit ['allow' '[' Rights ']'] ['as' Name]` единая для `"./utils"` и `"json@1.4"`; выполняется ли top-level код модуля при импорте; циклические импорты — ошибка (Go) или разрешены (Python); версии модулей — по решению фазы 1.
- Тайпчекер: когда (см. фазу 10).
- Готово: примеры этапа C в `examples/pending/` с метками фаз, таблица SPEC обновлена.

### Фаза 10. Минимальный тайпчекер (решение о подходе)
Два пути. A — как в PDF (шаг 8 после шага 7): весь этап C динамически, типы потом. Минус: ретрофит поверх 11 конструкций, часть тестов этапа C перепишется, большой «разлом». B (рекомендую): крошечный тайпчекер сейчас (int/float/string/bool, вывод для `let`, сигнатуры `fn`, аннотации), и в каждой следующей фазе под-шаг «типы для этой фичи». Этап E тогда — только сложное (сужение, вариативность, вывод generics). План ниже написан под путь B; если выберешь A, этап E получает под-шаги 25a–25d (базовые типы и сигнатуры; `throws`-анализ из фазы 14; null-safety из фазы 16; generics из фазы 17), а статические критерии фаз 14, 16, 17 переезжают туда.
- Тайпчекер проходит весь файл до исполнения; в REPL — каждый ввод с сохранением окружения типов.
- Читать: D. Christiansen «Bidirectional Typing Rules: A Tutorial» (локальный вывод, без Хиндли–Милнера).
- Готово: `var x = 5; x = "a"` → `error: expected int, found string`; `fn f(a: int)` вызванная со строкой → ошибка с подсказкой.

### Фаза 11. Строки
- Интерполяция через токены частей строки (решение фазы 4), escape-последовательности, вложенные кавычки `"{f("x")}"`, методы (`len`, `upper`, срезы). Модуль `strings` стандартной библиотеки начинается здесь — через `arete_rt.h` (фаза 3), в него добавляется API строк.
- Готово: тесты интерполяции; незакрытая `{` → ошибка с колонкой.

### Фаза 12. Коллекции
- 12a. `List`: литерал, индексация, срезы, `for` через протокол итерации (фаза 7a), методы; негативный тест: индекс вне диапазона.
- 12b. `Map` (хеш-таблица на C) и `Set`; протокол `equals/hash` для встроенных типов (data class в 15d его просто реализует).
- Решение об изменяемости из фазы 9 реализуется здесь. Модуль `collections` начинается здесь, в `arete_rt.h` добавляется API списков и словарей. Типы: `List<int>` в тайпчекере.
- Готово: тесты List/Map/Set; `let`-список и попытка изменить → ошибка по выбранному правилу.

### Фаза 13. when
- Все формы из фазы 9; блочные ветки; `when` как выражение (если решено в фазе 1). До проверки исчерпываемости (фаза 25) пропущенная ветка — ошибка рантайма, это записано.
- Минимальное сужение уже здесь: внутри ветки `is Type` субъект (локальный `let`) имеет этот тип; общее сужение в `if` — фаза 25. `T?` принимается как сахар для `T | null` с этой фазы, проверки null-safety — фаза 16.
- `is int` над `int | string` работает по тегу значения; над классами — RTTI (фаза 15).
- Типы: union как тип в тайпчекере — подтипирование `int <: int | string`, присваивание, аннотации; `T?` в фазе 16 станет частным случаем `T | null`. Негативный тест: `let x: int | string = true` → ошибка.
- Читать: Kotlin docs «when».
- Готово: тесты всех форм веток; `when` без `else` над не покрытым значением → понятная ошибка рантайма.

### Фаза 14. Ошибки
- `throws` у функции, `throw`, `try/catch` со встроенным `Error(message)`. Пользовательские типы ошибок — после классов (15f). Решения из фазы 9: typed throws, `finally/defer`, `rethrows`.
- Типы: вызов `throws`-функции вне `try` и без `throws` у вызывающей — ошибка компиляции (ключевое обещание PDF «компилятор не даст забыть»).
- Читать: Swift «Error Handling».
- Готово: позитивные тесты; `load(1)` без `try` → `error: call can throw but is not handled` с подсказкой «wrap in try or mark fn throws`.

### Фаза 15. Классы
- 15a. `class`, поля, методы, конструктор, `self`/`this` (твоё решение).
- 15b. Закрыты по умолчанию, `open`, наследование, `super`, переопределение. Негативный тест: наследование от закрытого класса.
- 15c. `interface` и реализация; встроенные `Comparable`, `Equatable`/`Hashable`, `Iterable` (нужны generics-ограничениям, Map/Set, `for in`).
- 15d. `data class`: `==`, строковое представление, `copy`, деструктуризация (решить).
- 15e. `enum` (и/или `sealed`) — питает исчерпываемость `when`.
- 15f. Свои типы ошибок на базе классов/`Error`.
- Читать: CI гл. 12–13; Kotlin docs «Data classes», «Sealed classes».
- Готово: у каждой под-фазы свой пример и негативный тест.

### Фаза 16. Null-safety
- `T?`, `??`, `?.` (теперь есть поля и методы), проверка `if x != null`.
- Статика: `string?` нельзя передать в `string` без проверки. Таблица умных приведений: локальные `let` — всегда; `var` — если нет присваиваний между проверкой и использованием и переменная не захвачена замыканием; поля — только `let`-поля того же модуля.
- Читать: Kotlin docs «Null safety», «Smart casts».
- Готово: `let s: string? = null; print(s.len)` → ошибка с подсказкой `use ?. or check for null`.

### Фаза 17. Generics
- Синтаксис для функций, классов, интерфейсов; ограничения `T: Comparable`; явные аргументы типов по решению фазы 9; модель reified/erasure по решению фазы 9.
- Типы: инстанцирование, вывод параметров из аргументов, проверка ограничений.
- Готово: `first<T>(xs: List<T>) -> T`, `Box<T>`; `max<T: Comparable>` с типом без `Comparable` → ошибка.

### Фаза 18. Модули
- Один файл = модуль, всё приватно, `pub`. `use "./utils"` по единой грамматике. Разрешение имён между файлами (резолвер + тайпчекер), версии в заголовках модулей по правилу фазы 1, семантика top-level кода модуля, циклы по решению фазы 9.
- Готово: `a.rt` подключает `b.rt`; приватная функция снаружи → `error: 'helper' is private`; цикл a↔b ведёт себя по решению фазы 9 (при варианте «ошибка» — `error: circular import`).

## ЭТАП F — Скорость и рантайм (PDF шаг 10, первая половина)

### Фаза 26. SPEC.md v4 — решения рантайма (четвёртая сессия)
Решаем вместе:
- Память: циклы при подсчёте ссылок — `weak` и/или сборщик циклов (trial deletion как в CPython). Последствие: сборщик циклов — это паузы, пусть короткие, то есть ревизия решения PDF «без пауз GC»; фиксировать в SPEC как «ревизия в фазе 26». Детерминированные деструкторы.
- Многопоточность: M:1 планировщик (зелёные потоки на одном ядре, неатомарный refcount, детерминизм — он же нужен для перемотки) на старте; M:N позже при правиле «через канал только неизменяемое или перемещённое». `spawn` возвращает ли дескриптор, есть ли `join`; что с `throws` внутри `spawn`; нужен ли `select` в первой версии.
- Макросы: маркер вызова (`swap!(a, b)`) или без маркера — тогда нужен отдельный проход сбора объявлений макросов до разбора вызовов (как в Nim), потому что аргументы макроса — места, а не значения; место раскрытия: parse → expand → resolve → typecheck.
- `unsafe`: синтаксис указателей (`*int` или `ptr<int>`), что разрешено только внутри, помечаются ли функции.
- Архитектура VM заранее: кадры и стек операндов в куче на задачу (не на C-стеке); исключения — таблицы диапазонов байткода с release локалов; переключения задач добавляются в слой `rt_effect_*` из фазы 21, и там же уточняется формат записи для перемотки.
- Третья ревизия CLAUDE.md: какие внешние зависимости разрешены с этого этапа (LLVM и т.д.).
- Готово: разделы «Память», «Задачи», «Макросы», «unsafe», «VM» в SPEC.
